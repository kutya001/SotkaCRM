# GEMINI.md — Генеральные инструкции и правила разработки SotkaCRM

## 1. Реестр документации и распределение зон ответственности

Система проектной документации SotkaCRM состоит из взаимосвязанных файлов-манифестов в корневой директории репозитория. Любые действия агента обязаны опираться на эти документы как на единый источник правды:

*   **`GEMINI.md`** — Главный координирующий регламент: архитектурные ограничения, рабочие алгоритмы агента, правила управления памятью и синхронизации документов[cite: 6].
*   **`ТЗ.md`** — Техническое задание: цели проекта, функциональные модули, сценарии конверсии лидов, алгоритмы начислений и этапы сдачи[cite: 9].
*   **`DB.md`** — Физическая спецификация СУБД (PostgreSQL / Supabase): DDL-схема, структуры таблиц, внешние ключи, типы `ENUM`, триггеры и политики безопасности RLS[cite: 5].
*   **`sotka-api.json`** — Контракты взаимодействия с внешним API `https://api.sotka.kg`: схемы запросов/ответов, маппинг полей, правила пагинации и нормализации данных[cite: 7].
*   **`UxUi.md`** — Спецификация визуального интерфейса: стиль Apple Island (Glassmorphism), мобильный/десктопный лейауты, универсальный реестр `DataJournal`, цветовая дифференциация и дизайн профилей[cite: 8].
*   **`.env.example`** — Стандарт именования конфигурационных переменных среды и ключей безопасности[cite: 4].
*   **`.antigravity/`** — Изолированное хранилище рабочих контекстов агента (планы, отчеты, архивы промежуточных ТЗ)[cite: 6].

## 2. Протокол непрерывной актуализации документации

При выполнении любых задач агент обязан автоматически поддерживать документацию в актуальном состоянии без отдельных напоминаний:

*   **Синхронизация базы данных (`DB.md`):**
    *   При любом изменении схемы (добавление колонки, смена типа данных, создание индекса, триггера, функции или RLS-политики) агент обязан незамедлительно вносить эти правки в `DB.md`[cite: 5, 6].
    *   Запрещено применять миграции в коде, не зафиксировав актуальную сигнатуру в `DB.md`[cite: 5, 6].
*   **Синхронизация контрактов API (`sotka-api.json`):**
    *   При изменении маршрутов, параметров пагинации, добавлении новых эндпоинтов или трансформации маппинга внешних данных в таблицы Supabase агент обязан обновлять `sotka-api.json`[cite: 7].
*   **Синхронизация интерфейса (`UxUi.md`):**
    *   При добавлении новых пользовательских экранов, корректировке фильтров компонента `DataJournal`, переработке структуры карточек или внедрении новых дизайн-токенов агент обязан фиксировать изменения в `UxUi.md`[cite: 8].
*   **Синхронизация переменных окружения (`.env.example`):**
    *   При внедрении любых новых внешних сервисов, ключей или серверных переменных агент обязан сразу добавлять их плейсхолдеры в `.env.example`[cite: 4].

## 3. Ключевые бизнес-правила и инварианты целостности

1.  **Неизменяемость реестра лидов:**
    *   Физическое удаление (`DELETE`) записей из таблицы `leads` строго запрещено на уровне триггера базы данных `prevent_lead_delete` и клиентского кода[cite: 5, 6, 9].
    *   Исключение лида из активной воронки оформляется исключительно переводом в статус: `status = 'Отмена'`[cite: 5, 6, 9]. Метод `supabase.from('leads').delete()` запрещен к генерации[cite: 6].
2.  **Жизненный цикл сделки (Воронка):**
    *   Статусы лида принимают строго значения из `ENUM`: `Открыт` → `Обработан` → `Назначен` → `Подписан` | `Отмена`[cite: 5, 6, 9].
3.  **Изоляция и ручное связывание «Лид → Продавец»:**
    *   Связывание выполняется вручную по внешнему ключу `leads.seller_phone = sellers.seller_phone`[cite: 5, 6, 9].
    *   В выборке свободных продавцов для привязки отображаются только те, чей номер телефона отсутствует в поле `seller_phone` таблицы `leads`[cite: 5, 6, 9].
    *   Успешная привязка продавца автоматически переводит статус лида в `Подписан` и проставляет метку времени `linked_at`[cite: 5, 6, 9].
4.  **Синхронизация с API `api.sotka.kg`:**
    *   Запуск синхронизации разрешен **исключительно роли `admin`**[cite: 6, 9].
    *   Синхронизация выполняется только через серверный Next.js Route Handler (`/api/sync/sotka`)[cite: 6, 9]. Прямые вызовы API Sotka с клиента запрещены[cite: 6].
    *   Операция upsert в таблицу `sellers` обязана сохранять локально назначенных менеджеров (`manager_id`), не затирая их[cite: 5, 7, 9].

## 4. Ролевая модель доступа (RBAC & RLS)

Доступ к интерфейсу и данным разделяется на основании роли в таблице `users.role`[cite: 5, 6]:

*   **`admin` (Администратор):**
    *   Полный доступ ко всем модулям системы, настройкам тарифных планов (`plans`), индивидуальным ставкам (`employee_rates`) и выплатам (`employee_payouts`)[cite: 5, 6, 9].
    *   Единоличное право инициации API-синхронизации с `api.sotka.kg`[cite: 6, 7, 9].
*   **`consultant` (Продавец-консультант):**
    *   Просмотр нераспределенных лидов и лидов, где `assigned_to` равен его `user_id`[cite: 5, 6, 9].
    *   Движение лидов по воронке, ручное связывание со свободными продавцами[cite: 6, 9].
    *   Просмотр закрепленных за собой клиентов в `sellers`, аналитика собственных комиссий[cite: 5, 6, 9].
    *   Запрещен доступ к глобальным финансовым расчетам и синхронизации[cite: 6, 9].
*   **`smm` (SMM-специалист):**
    *   Создание новых входящих карточек лидов через мобильную FAB-кнопку или форму[cite: 6, 8, 9].
    *   Просмотр только тех лидов, где `created_by = current_user_id`[cite: 5, 6, 9].
    *   Запрещен доступ к базам продавцов, платежей, тарифов и выплат[cite: 6, 9].

## 5. Требования к UI/UX и интерфейсным компонентам

Интерфейс обязан полностью соответствовать спецификации `UxUi.md`[cite: 8]:

*   **Стиль Apple Island (Glassmorphism):**
    *   Плавающие матовые островки со скруглением `rounded-2xl` или `rounded-3xl`[cite: 8].
    *   Стекло: `backdrop-blur-xl bg-white/75 border border-white/20` (светлая тема) и `backdrop-blur-xl bg-zinc-900/75 border border-zinc-800/40` (тёмная тема)[cite: 8].
*   **Линейный стиль иконок:**
    *   Использование исключительно контурных векторных иконок пакета **Lucide React** (`stroke-width="1.75"` или `2`)[cite: 8].
    *   **Категорический запрет на использование эмодзи** во всех элементах интерфейса (кнопки, статусы, лейблы, уведомления)[cite: 8].
*   **Адаптивная архитектура лейаута:**
    *   **Десктоп (от 1024px):** Фиксированный скрываемый боковой матовый сайдбар + плавающий верхний островок Top Header + скроллируемый центральный контейнер[cite: 8].
    *   **Мобильные устройства (до 1023px):** Верхняя матовая панель с заголовком, кнопками поиска (лупа) и фильтра + нижний плавающий бар навигации (Bottom Bar) + круглая плавающая кнопка добавления (FAB `w-14 h-14`) в правом нижнем углу под большой палец[cite: 8].
*   **Полиморфный компонент `DataJournal`:**
    *   Единый реестр для всех сущностей (Лиды, Продавцы, Транзакции, Выплаты)[cite: 8].
    *   **ПК-режим по умолчанию:** Табличный вид (`Table View`) со sticky-шапкой, изменением ширины столбцов, drag-and-drop сортировкой колонок и настройкой их видимости[cite: 8].
    *   **Мобильный режим по умолчанию:** Карточный вид (`Card View`) с кнопками связи в 1 клик (`tel:`, WhatsApp `wa.me`, Instagram Direct), in-place переключением статуса через dropdown и скрытием второстепенных полей[cite: 8].
    *   Универсальный конструктор фильтров, сортировка по любому атрибуту и серверная настраиваемая пагинация[cite: 8].
*   **Цветовая индикация и персональный профиль:**
    *   Фиксированная палитра статусов воронки (лазурный, фиолетовый, янтарный, изумрудный, серый)[cite: 8].
    *   Индивидуальные цветовые бейджи ответственных сотрудников[cite: 8].
    *   Профиль пользователя с переключателем темы оформления и KPI-дашбордом под соответствующую роль[cite: 8].

## 6. Регламент управления памятью и структурой каталога `.antigravity/`

Для исключения перегрузки активного контекста диалога агент изолирует промежуточные файлы в директорию `.antigravity/` по строгим категориям[cite: 6]:

### 6.1. Категории директории `.antigravity/`
*   `.antigravity/planning/` — Декомпозиция задач, проектные планы, архитектурные рассуждения перед созданием или изменением кода[cite: 6].
*   `.antigravity/results/` — Отчеты о выполненных этапах, протоколы ручной или автоматической верификации функционала[cite: 6].
*   `.antigravity/archive/` — Отработанные технические задания, временные инструкции и устаревшие спецификации[cite: 6].

### 6.2. Стандарт именования файлов
Каждый создаваемый или перемещаемый файл внутри `.antigravity/` обязан содержать временную метку по шаблону[cite: 6]:
```text
[название_файла]-[ДД-ММ-ГГГГ]-[ЧЧ-ММ-СС].md

```

* Формат даты: день (`ДД`), месяц (`ММ`), год (`ГГГГ`) в 4 цифры.


* Формат времени: часы (`ЧЧ`), минуты (`ММ`), секунды (`СС`) в 24-часовом формате.


* *Примеры валидных имен:*
* `.antigravity/planning/data_journal_refactor-19-09-2026-15-20-45.md`
* `.antigravity/results/sync_sotka_verified-19-09-2026-17-05-12.md`
* `.antigravity/archive/leads_mobile_tz-19-09-2026-18-40-00.md`



### 6.3. Правило чистой корневой директории

* В корне проекта разрешено находиться только рабочим файлам сборки (`package.json`, `next.config.js` и т.д.) и постоянным манифестам: `GEMINI.md`, `ТЗ.md`, `DB.md`, `UxUi.md`, `sotka-api.json`, `.env.example`.


* Любые разовые ТЗ, пользовательские заметки или временные инструкции после интеграции в код обязаны сразу перемещаться в `.antigravity/archive/` с присвоением таймштампа.

## 7. Технические стандарты разработки

* **Клиент/Сервер:** Директива `'use client'` используется только в компонентах с интерактивностью. Серверные ключи (`SUPABASE_SERVICE_ROLE_KEY`, `SOTKA_API_PASSWORD`) импортируются исключительно в Server Actions и Route Handlers.


* **Типизация:** Все обращения к базе данных типизируются сгенерированным интерфейсом `types/database.types.ts`.


* **Скрипты продаж:** Модуль быстрых регламентов работает через Bottom Sheet с копированием в буфер обмена и вызовом виброотклика `navigator.vibrate(50)`.
