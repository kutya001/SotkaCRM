**Техническое задание (ТЗ) на разработку системы SotkaCRM**

**1. Общие положения**

* **Наименование проекта:** SotkaCRM.
* **Тип приложения:** Веб-приложение (Single Page Application / Progressive Web App).
* **Среда эксплуатации:** Мобильные устройства (приоритет — Mobile-First) и десктопные браузеры.
* **Модель развертывания:** Vercel (Hosting/Serverless) + Supabase (BaaS/PostgreSQL) + GitHub (VCS).

**2. Назначение и цели системы**
SotkaCRM предназначена для автоматизации работы отдела продаж, операторов SMM и административного персонала.
Ключевые цели:

1. Учет и ведение входящих лидов (SMM -> Консультант).
2. Синхронизация базы зарегистрированных продавцов и транзакций с внешним API (`api.sotka.kg`).
3. Ручное связывание конвертированного лида с зарегистрированным аккаунтом продавца.
4. Автоматизация расчета комиссионных вознаграждений (за подключение и сопровождение) и учет выплат сотрудникам.
5. Обеспечение контроля доступа к данным на основе ролевой модели (RBAC).

**3. Архитектура и стек технологий**

* **Frontend:** React, Next.js (App Router), Tailwind CSS.
* **Backend / API:** Next.js Serverless Route Handlers.
* **База данных:** PostgreSQL (хостинг Supabase).
* **Аутентификация:** Supabase Auth (Email/Password).
* **Интеграция:** REST API (`api.sotka.kg`).
* **Ограничения целостности:** Управление логикой на уровне СУБД (PostgreSQL Triggers, RLS - Row Level Security).

**4. Ролевая модель и управление доступом (RBAC)**
Система включает три жестко заданные роли (таблица `users.role`):

1. **Администратор (`admin`)**
* Полный доступ ко всем таблицам и модулям (CRUD).
* Управление доступом (создание/блокировка пользователей).
* Исключительное право запуска синхронизации с API.
* Управление справочниками (тарифы, процентные ставки сотрудников).
* Проведение финансовых выплат (`employee_payouts`).


2. **Продавец-консультант (`consultant`)**
* Просмотр списка свободных лидов и лидов, назначенных на него.
* Изменение статуса лида (движение по воронке).
* Связывание лида с продавцом (маппинг).
* Просмотр списка свободных продавцов (для привязки) и продавцов из своего портфеля.
* Просмотр собственных начислений.
* Запрет на удаление данных, запрет на вызов API-синхронизации.


3. **SMM-специалист (`smm`)**
* Создание новых карточек лидов.
* Просмотр только созданных им лидов.
* Запрет на изменение статусов (кроме перевода ошибочных в «Отмена» до взятия в работу).
* Запрет на просмотр базы продавцов и финансов.



**5. Требования к UI/UX (Mobile-First)**

* **Омниканальность в 1 клик:** В карточке лида должны быть активные кнопки:
* Вызов: `tel:{country_code}{phone}`
* WhatsApp: `[https://wa.me/](https://wa.me/){country_code}{phone}`
* Instagram: Переход по ссылке или открытие приложения по `@username`.


* **Навигация по воронке:** Горизонтальные свайпы для переключения вкладок статусов лидов (Открыт, Обработан, и т.д.).
* **In-place редактирование:** Изменение статуса лида через выпадающий список (Dropdown) прямо в ленте списка карточек, без перехода на детальную страницу.
* **Быстрое действие:** Плавающая кнопка (FAB - Floating Action Button) в правом нижнем углу экрана для быстрого добавления нового лида.
* **Интеграция скриптов:** Модуль базы знаний со скриптами продаж. Нажатие на текст скрипта копирует его в буфер обмена с виброоткликом (Haptic Feedback) для быстрой вставки в Direct/WhatsApp.

**6. Функциональные требования по модулям**

**6.1. Модуль «Лиды» (`leads`)**

* **Ввод данных:** Форма создания лида SMM-специалистом (ФИО, Телефон без кода, Код страны, Instagram, Комментарий).
* **Воронка статусов (Enum):** `Открыт` -> `Обработан` -> `Назначен` -> `Подписан` -> `Отмена`.
* **Защита данных (СУБД):** Триггер `prevent_lead_delete`, блокирующий выполнение операции `DELETE`. Допустимо только изменение статуса на `Отмена`.
* **Логика связывания (Маппинг):**
* Если лид успешно сконвертирован, консультант нажимает «Связать с продавцом».
* Открывается модальное окно/селектор со списком зарегистрированных продавцов.
* **Ограничение выборки:** В список попадают только продавцы из таблицы `sellers`, поле `seller_phone` которых отсутствует в столбце `seller_phone` таблицы `leads` (продавец не должен быть привязан к другому лиду).
* При выборе продавца происходит `UPDATE` записи лида: статус меняется на `Подписан`, записывается `seller_phone`, фиксируется `linked_at`.



**6.2. Модуль «Синхронизация API» (Только `admin`)**

* **Процесс:** Вызов Next.js Route (`/api/sync/sotka`).
* **Авторизация:** Проверка токена Supabase (пользователь) -> проверка роли (`admin`).
* **Интеграция:**
1. Отправка POST-запроса на `/api/public/v1/auth/pair` с кредами администратора из `.env`.
2. Извлечение Bearer-токена.
3. Цикличный GET-запрос с пагинацией (`limit=100`, `offset`) на `/api/private/v1/admin/sellers-overview/` и `/api/private/v1/admin/transactions/`.
4. Запись в Supabase таблиц `sellers` и `payments` методом `Upsert` (по ключам `seller_phone` и `payment_id`). Существующие связи в CRM (ответственные менеджеры) не перезаписываются при конфликте.
5. POST-запрос на `/api/public/v1/auth/logout`.



**6.3. Модуль «Связи и подключения» (`connections`)**

* **Создание связи:** Закрепление продавца за консультантом. Модель 1:1. Отражается в `connections`.
* **Расчет комиссии за подключение:** При создании связи система вычисляет сумму комиссии: `Базовая стоимость тарифа (plans.price) * Процент за подключение (employee_rates.connection_percent) / 100`.
* **Учет SLA сопровождения:** Фиксация количества месяцев сопровождения (лимит до 3 месяцев).

**6.4. Модуль «Финансы и выплаты» (`client_maintenance`, `employee_payouts`)**

* **Биллинг:** Ежемесячная генерация записей в `client_maintenance` для активных связей (расчет 10% от стоимости тарифа).
* **Журнал выплат:** Администратор фиксирует транзакции выдачи средств сотрудникам в `employee_payouts` с указанием типа (аванс, ЗП, бонус), суммы и метода оплаты.

**6.5. Модуль «Справочники и география»**

* Управление тарифами платформы (`plans`). При изменении цены старая запись логируется в `plans_history`.
* Таблица `outlets` для фиксации физических точек (широта, долгота) привязанных к продавцам.

**7. Требования к базе данных**
Схема реализована в PostgreSQL.

* Включить RLS (Row Level Security) в Supabase для всех таблиц для дополнительного уровня безопасности.
* **Нормализация телефонов:** Телефоны хранятся строго в виде цифр.
* **Ограничения целостности:**
* `leads.seller_phone` -> `UNIQUE`, `FOREIGN KEY REFERENCES sellers(seller_phone) ON DELETE SET NULL`.
* Внешние ключи для `assigned_to`, `created_by` к таблице `users`.



**8. Окружение и развертывание**

* **Vercel Environment Variables:**
* `NEXT_PUBLIC_SUPABASE_URL`
* `NEXT_PUBLIC_SUPABASE_ANON_KEY`
* `SUPABASE_SERVICE_ROLE_KEY`
* `SOTKA_API_PHONE` (для авторизации в api.sotka.kg)
* `SOTKA_API_PASSWORD`


* **Ветвление:** Master (Production) -> Vercel автоматический деплой при `git push`.

**9. Порядок сдачи-приемки работ**

1. **Этап 1:** Инициализация репозитория, настройка Supabase (создание таблиц, типов, триггеров, политик RLS). Настройка авторизации.
2. **Этап 2:** Разработка модуля «Лиды» (CRUD, UI мобильной версии, свайпы, кнопки мессенджеров, скрипты).
3. **Этап 3:** Разработка серверной части (Serverless API) для интеграции с `api.sotka.kg`. Настройка механизма Upsert.
4. **Этап 4:** Разработка модулей маппинга продавцов и управления связями.
5. **Этап 5:** Разработка финансового блока, справочников и админ-панели. Тестирование и деплой на Production.
